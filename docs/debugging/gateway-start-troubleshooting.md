# Gateway start troubleshooting

Established from a live failure on real hardware (2026-10-16,
v0.1.31) and verified against the code. The data directory below is
`%APPDATA%\local-llm-service-manager` by default
(`C:\Users\<user>\AppData\Roaming\local-llm-service-manager`).

## "A setup step is already running"

The install wizard holds one lock for the whole duration of a step
(install LiteLLM, start the gateway, and so on), so a step that
never finishes blocks every later attempt with this message for the
rest of the session.

Pre-v0.1.32 there were no timeouts anywhere in the chain: a stalled
child process — observed with `uv pip install` and with the Prisma
engine pre-warm (`python -m prisma --version`, which downloads
engines and a Node runtime on first use) — held the lock forever.
Restarting the app cleared the lock, but the next attempt at the
same step re-entered the same unbounded phase and appeared to hang
again.

v0.1.32 behavior:

- Step budgets: start-gateway 10 minutes, other steps 5 minutes. A
  step that exceeds its budget is killed and fails with a named
  outcome instead of hanging.
- Subprocess timeouts underneath the budgets (10 minutes by
  default, 15 minutes for package installs and Prisma generation).
- The busy message names the running step and how long it has been
  running ("start-gateway has been running for 12 min — …"), and
  every rejection is appended to the wizard log.

Where to look: the Logs view, `wizard` scope, or
`<data_dir>\logs\wizard.log`. Every step writes a start marker and a
finish block (state, message, log tail). A start marker with no
finish block is the tell for a wedged step. The diagnostics export
bundle includes `logs/wizard.log` from v0.1.32.

## Gateway won't start with a database configured

Signature in the gateway logs (and, from v0.1.32, in the
start-gateway step's failure message, which appends the tail of
`logs\gateway.stderr.log` when the health check fails):

```
RuntimeError: The Client hasn't been generated yet, you must run `prisma generate`
```

Cause: when app-managed PostgreSQL is installed, the gateway is
spawned with `DATABASE_URL` set, and LiteLLM imports its Prisma
client during startup to talk to that database. The client is
generated code that must be produced once per venv by
`prisma generate`; the wizard historically never ran it (its only
Prisma touch was a `python -m prisma --version` pre-warm, which
generates nothing), so the gateway died in its lifespan about a
second after startup.

Why it only happens with a database: without `DATABASE_URL`,
LiteLLM never imports Prisma and starts fine. Verified live: the
same venv and config ran the gateway indefinitely with
`DATABASE_URL` unset and died within ~1 s with it set.

What was ruled out during the investigation (do not re-chase):

- PostgreSQL itself. The app's own `psql` against the app's
  `DATABASE_URL` (`select 1;`) returned a row: server running, port
  (`postgres.port` in config.json — 54329 in the recorded incident),
  password, and the `litellm` database all correct, and the app's
  URL construction (`postgres_database_url`) proven good.
- Prisma version skew. Versions from the affected venv:

  | Package | Version |
  | --- | --- |
  | litellm | 1.105.1 |
  | prisma (prisma-client-py) | 0.15.0 |

  LiteLLM declares `prisma>=0.11.0,<1.0` under its `extra-proxy`
  extra (prisma is not part of `litellm[proxy]`, which is why the
  wizard installs it separately). The installed 0.15.0 satisfies
  that range, and the client had been generated by that same
  0.15.0 — generator/runtime version skew is ruled out. The
  pairing itself is nonetheless one of the two defects (third
  signature below): a satisfied declared range is exactly what
  made it non-obvious.

### Second signature: `spawn prisma-client-py ENOENT`

```
Error: spawn prisma-client-py ENOENT
```

Running `prisma generate` manually against a venv that has not
been activated fails this way after the schema loads: the Prisma
CLI spawns the Python generator executable `prisma-client-py` by
name, and it lives in the venv's `Scripts` directory, which is not
on `PATH` unless the venv is activated. Remedy: prepend the venv's
`Scripts` directory to the child process `PATH` (in PowerShell:
`$env:PATH = "<data_dir>\python\venv\Scripts;$env:PATH"`). The
app's own generate invocation does this from v0.1.32.

### Third signature: `_Prisma__engine` at connect()

```
LiteLLM Proxy:WARNING: utils.py:5749 - LiteLLM Prisma Client Exception connect(): 'Prisma' object has no attribute '_Prisma__engine'
```

The client imports, then fails when LiteLLM connects it. A plain
`from prisma import Prisma` import succeeds — the failure only
fires at `connect()` — so an import check cannot detect it.

Root cause (defect 1 of 2 — a version incompatibility inside
LiteLLM's wrapper): LiteLLM 1.104/1.105's PrismaWrapper
(`litellm/proxy/db/prisma_client.py`) reads and writes the
generated client's name-mangled `_Prisma__engine` attribute.
prisma-client-py PRs #873/#876 moved connect/disconnect/query
execution into a new `BasePrisma` base class; from 0.13.0 on, the
generated `Prisma` class no longer defines `_Prisma__engine`, so
the wrapper's connect raises `AttributeError`. A process kill
cannot produce a missing-attribute error — this defect is
independent of the watchdog defect below.

Established by field testing (2026-10-16):

- Reproduced on prisma 0.15.0; absent on 0.11.0.
- It is not a package left half-written by an interrupted
  generate: a clean reinstall of `prisma==0.15.0` followed by a
  fresh generate reproduced the identical error. Ruled out.
- The client itself is not defective: a standalone
  `Prisma().connect()` with the same venv and the same
  `DATABASE_URL` succeeds ("prisma connect OK"). Client, engine,
  database, and URL are all cleared by that test — the wrapper is
  LiteLLM-side code, and the raw client never touches the
  attribute the wrapper wants.
- On 0.15.0 with the watchdog disabled (fourth signature), the
  gateway stays up but still logs this warning at every start:
  the connect exception is survivable but real, and the wrapper's
  database path remains suspect.

Fix: the exact pin `prisma==0.11.0` — LiteLLM's own
pyproject/lockfile pin for the proxy, and the version multiple
production deployments pin for this exact incompatibility. Not a
range cap: 0.12/0.13 are untested against LiteLLM, and 0.13 is
already known-broken. A configuration that logs a Prisma client
exception at every start is not the shipped default when
LiteLLM's own lockfile pin is clean. The wizard installs the pin
and enforces it on the `DATABASE_URL` path (see "What v0.1.32
does automatically" below).

### Fourth signature: starts, then silently shuts down ~1 s later (Windows)

With `DATABASE_URL` set, the gateway reaches "Application
startup complete", then logs a graceful shutdown ("Waiting for
application shutdown. / Application shutdown complete.") about
a second later — no error, no traceback. Without `DATABASE_URL`
it runs indefinitely. In the recorded incident this presented
together with the third signature; they are separate defects
with separate fixes.

Root cause (defect 2 of 2 — the Prisma health watchdog):
LiteLLM's proxy runs a background watchdog (`_poll_engine_proc`,
introduced by LiteLLM PR #21899, with win32 routed into the poll
by PR #23494) that periodically probes whether the query-engine
process is alive by calling `os.kill(pid, 0)`. On Linux/macOS,
signal 0 is a harmless existence probe. On Windows, CPython's
`os.kill` routes to `TerminateProcess` — the "probe" kills the
engine on the very first poll. The proxy reads the dead engine
as a lost database connection and shuts Uvicorn down cleanly,
which is why the shutdown is graceful and silent: from the
server's side it is an orderly stop, not a crash. References:
BerriAI/litellm issues #25260, #30847, #26886.

Why a standalone Prisma client is unaffected: the watchdog is
LiteLLM-side code, not part of prisma-client-py. The isolation
test's connected client stayed alive through a 15 s sleep; only
the proxy runs the poll.

Remedy: `PRISMA_HEALTH_WATCHDOG_ENABLED=false` in the gateway
process's environment. Field retest matrix (2026-10-16):

| prisma | Flag | Result |
| --- | --- | --- |
| 0.15.0 | unset | `_Prisma__engine` warning, then shutdown ~1 s after startup |
| 0.15.0 | `false` | stays up; the `_Prisma__engine` warning is still logged at every start |
| 0.11.0 | `false` | stays up; startup completely warning-free |

So the flag alone cures the shutdown on both versions; the pin
is what removes the connect exception. Both ship.

Downsides of running with the watchdog disabled: if PostgreSQL
or the query engine dies later, the proxy does not heal itself —
database features stay down until the gateway is restarted — and
Prometheus database metrics are not collected. Acceptable for an
app-supervised single-node gateway: the app owns gateway
restarts, and the alternative on Windows is a watchdog that
kills the engine it monitors.

What v0.1.32 does automatically in the start-gateway step:

1. On the `DATABASE_URL` path, enforce the prisma pin before
   anything else: read the installed prisma-client-py version;
   on a mismatch, remove the `prisma` package directory from the
   venv's site-packages, reinstall `prisma==0.11.0`, and continue
   to generation. The directory removal matters: generated
   Prisma files are not installer-tracked, so they survive
   reinstalls and version changes, and a stale generated client
   crashes imports with errors from the wrong version (observed:
   after a manual 0.15.0 → 0.11.0 downgrade, importing prisma
   died with `AttributeError: module 'prisma._types' has no
   attribute 'SortMode'` until the package directory was deleted
   and the package reinstalled).
2. Probe by importing the client and connecting it against the
   real `DATABASE_URL`. Healthy probe → skip generation (the
   fast path on later starts).
3. Probe fails → resolve LiteLLM's schema and run
   `prisma generate`, then re-probe. This closes the
   not-generated failure above.
4. If the client still does not connect standalone after a
   successful generate, the step fails with the probe output in
   the message instead of spawning a gateway that cannot use its
   database. Note the probe alone cannot catch the third
   signature (standalone connect succeeds in that state) — the
   pin in step 1 is what closes it.
5. The spawn environment carries `DATABASE_URL` and, on
   Windows, `PRISMA_HEALTH_WATCHDOG_ENABLED=false`. Every start
   route (Setup Wizard, Gateway view, activation-plan restart)
   runs this same step, so all of them get both.
6. After the first healthy probe on the database path, the step
   keeps confirming health for ~10 s before reporting success:
   both defects strike about a second after a plain connect
   succeeds, so a single successful probe cannot distinguish a
   healthy gateway from one that is about to die.

### Migrations are a separate, post-connect concern

`prisma migrate deploy` and `prisma db push` are non-remedies
for every failure in this document: LiteLLM applies its schema
itself at startup when it connects, the pip package ships no
migrations to deploy, and the recorded incident's tables were
already present. Migrations did not cause any of the failures
above: connecting precedes schema interaction, and the
standalone connect test succeeded against the database in its
unmigrated state. For completeness, the migration state of a
pip-installed LiteLLM 1.105.1, verified live:

- `python -m prisma migrate status --schema <schema>` reports "No
  migration found in prisma/migrations" and, vacuously, that the
  database is up to date: the pip package ships no
  `prisma/migrations` directory, so `prisma migrate deploy` has
  nothing to apply and is a no-op for this install form.
- The tables themselves are present in the recorded incident's
  database (`LiteLLM_UserTable`, `LiteLLM_SpendLogs`, and the rest
  of the LiteLLM schema) — confirmed by inspection. Schema state
  is not a factor in any failure in this document, and the
  start-gateway step performs no migration action: there is
  nothing for `migrate deploy` to apply on a pip install.

### Manual remedy (v0.1.31 installs)

Three parts: generate the client, pin prisma, and disable the
watchdog. From a PowerShell window, with the venv's `Scripts`
directory on `PATH` (previous section) and `DATABASE_URL` set
(next section):

```powershell
$schema = & "<data_dir>\python\venv\Scripts\python.exe" -c "import litellm, pathlib; print(pathlib.Path(litellm.__file__).parent / 'proxy' / 'schema.prisma')"
& "<data_dir>\python\venv\Scripts\python.exe" -m prisma generate --schema $schema
```

If the installed prisma-client-py is not 0.11.0 (check with
`importlib.metadata.version('prisma')`), the generated files
from the other version survive a plain reinstall and crash
imports (see the stale-client note under "What v0.1.32 does
automatically"), so remove the package directory first, then
install the pin and regenerate:

```powershell
Remove-Item "<data_dir>\python\venv\Lib\site-packages\prisma" -Recurse -Force
& "<data_dir>\bin\uv.exe" pip install --python "<data_dir>\python\venv\Scripts\python.exe" --reinstall-package prisma "prisma==0.11.0"
& "<data_dir>\python\venv\Scripts\python.exe" -m prisma generate --schema $schema
```

And in the window that starts the gateway (next section), set
`$env:PRISMA_HEALTH_WATCHDOG_ENABLED = "false"` alongside
`DATABASE_URL`, or the gateway shuts down silently about a
second after startup on Windows.

The schema can also be found by searching the venv's LiteLLM
package:

```powershell
Get-ChildItem "<data_dir>\python\venv\Lib\site-packages\litellm" -Recurse -Filter schema.prisma
```

## Every activation plan restarts the gateway, even backend-only ones

Signature: applying an activation plan whose changes are all
backend-scoped still stops and restarts the gateway, and the plan
shows "Gateway config: drifted" again immediately afterwards. A
gateway restart never clears the state.

Cause (fixed after v0.1.36, tracker #42): two drift definitions
diverged. The start-gateway step writes `gateway/config.yaml` from
the armed-only MCP view of the config (a Gateway-exposure MCP
server whose credential cannot be resolved is omitted from that
start), and the wizard's currency check compares against that same
view. The activation plan's drift check
(`activation::config_drift`) instead generated from the raw
registry, whose YAML always contains the unarmed server's
`mcp_servers:` block — a permanent mismatch against the file on
disk whenever a Gateway server was configured but unarmed (the
default state of the seeded `brave_search` until its Brave
credential is stored). Drift while the gateway is up makes every
plan gateway-pending, so both apply paths restarted the gateway.

Fix: the activation drift check and the gateway-change journaling
comparison both generate from the armed-only view, with arming
resolved by credential presence — the one rule, shared with the
wizard check. The activation drift check also compares the
`llmdil_routing.py` sibling, as the wizard check always did.

Note on restart cost: a gateway restart runs the start-gateway
step, which is verify-first on a healthy install — the venv is
reused when its probes pass (pinned Python, LiteLLM importable),
packages are installed only when the import probe fails, and the
Prisma client is verified (pin, generated client, connect probe)
before any repair runs. The step's minutes are the verification
probes plus LiteLLM's own cold boot, not a reinstall; the step log
(`logs/wizard.log`) states which path was taken ("reusing existing
venv", "Prisma install verified … — no changes made").

## Starting the gateway manually (PowerShell)

For console-visible diagnosis. Run the app (and this window)
unelevated: `postgres.exe` refuses to run under an administrative
token.

1. Read the two secrets from Windows Credential Manager. Targets:

   - `local-llm-service-manager/litellm-master-key`
   - `local-llm-service-manager/postgres-password`

   Route: Control Panel → Credential Manager → Windows Credentials
   → Generic credentials → the entry → Show (requires the Windows
   sign-in password or PIN). `cmdkey /list` can confirm an entry
   exists but cannot display its value.

2. Set the environment in the PowerShell window (port is
   `postgres.port` from `<data_dir>\config.json`):

   ```powershell
   $env:LITELLM_MASTER_KEY = "<master key>"
   $env:DATABASE_URL = "postgresql://postgres:<postgres password>@127.0.0.1:<port>/litellm"
   $env:PRISMA_HEALTH_WATCHDOG_ENABLED = "false"
   ```

   The watchdog line is required on Windows whenever
   `DATABASE_URL` is set (fourth signature above); the app sets
   it for its own spawns from v0.1.32.

3. Generate the Prisma client if this venv has never had it (see
   the remedy above).

4. Start PostgreSQL (the `&` call operator is required before a
   quoted executable path):

   ```powershell
   & "<data_dir>\postgres\bin\pg_ctl.exe" -D "<data_dir>\postgres\data" -l "<data_dir>\logs\postgres.log" -o "-p <port> -h 127.0.0.1" start
   ```

5. Start the gateway (host and port are `gateway.bind_host` and
   `gateway.port` in config.json):

   ```powershell
   & "<data_dir>\python\venv\Scripts\python.exe" -c "import sys; from litellm import run_server; sys.exit(run_server())" --config "<data_dir>\gateway\config.yaml" --host 0.0.0.0 --port 4000
   ```

   `python.exe` keeps a console with live output — use it for
   diagnosis. The app spawns `pythonw.exe` instead: detached, no
   console, output captured to `logs\gateway.stdout.log` /
   `logs\gateway.stderr.log`.

6. Leave the console window running. The gateway serves until the
   process is stopped. A trace ending in

   ```
   Waiting for application shutdown.
   Application shutdown complete.
   ```

   is a graceful stop (Ctrl+C or the window closing), not a crash.
   Exception: if it appears on its own about a second after
   startup with `DATABASE_URL` set, that is the watchdog defect
   (fourth signature above), not a stop you initiated.

## Log locations

| Log | Where | Contents |
| --- | --- | --- |
| Wizard log | Logs view `wizard` scope; `<data_dir>\logs\wizard.log` (rotates to `wizard.prev.log`) | Setup step start/finish blocks, step log tails, busy rejections (v0.1.32). Included in the diagnostics export bundle from v0.1.32. |
| Gateway stdout/stderr | `<data_dir>\logs\gateway.stdout.log`, `gateway.stderr.log` (previous spawn kept as `.prev`) | The gateway process's captured output; the start-gateway health-check failure appends the stderr tail to its message (v0.1.32). Also in the Logs view `gateway` scope. |
| PostgreSQL | `<data_dir>\logs\postgres.log` | PostgreSQL server log (the `pg_ctl -l` target). |
| Backend logs | Logs view, one scope per backend | Per-backend llama.cpp ring-buffer logs. |
