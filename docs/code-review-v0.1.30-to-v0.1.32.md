### Top 5 findings

1. **Blocker — DXGI descriptor struct is 8 bytes too small; `GetDesc1` overflows it on every poll.** `crates/manager-telemetry/src/pdh.rs:320-332`. The locally declared `DxgiAdapterDesc1` omits the trailing `Flags: u32` of the real `DXGI_ADAPTER_DESC1` (304 vs 312 bytes), so the WDDM telemetry fixup writes past a stack value every poll, in exactly the configuration the feature was built for.
2. **Major — Activation journal: `record_change`/`cancel_target` were never moved to scoped resolution.** `src-tauri/src/activation.rs:124-139, 199-225, 250-270`. Resolved backend entries never prune and the snapshot never resets, so cancelling a later change can silently revert an earlier, already-live change; the journal also grows monotonically.
3. **Major — Verified-by-stamp audit skip binds the stamp to nothing.** `crates/manager-wizard/src/steps.rs:1712-1745`. The skip checks only that a timestamp exists and the file length equals the catalog size — never the pinned hash — so a same-length corrupted or swapped GGUF is reported "checksum verified" on every launch, indefinitely, defeating the fail-closed backend-start gate.
4. **Major — Timeout budgets are mutually inconsistent; the 900 s sub-budgets are unreachable.** `crates/manager-wizard/src/ops.rs:32,462`, `src/lib.rs:488,1131`, `src/steps.rs:3485,3630,3992`. `run_command` caps every command at 600 s regardless of the caller's budget and the start-gateway step budget is 600 s total, so a legitimate cold install (400 s pip + 300 s generate) is killed mid-generate as a generic timeout.
5. **Major — Step timeouts do not terminate process trees, and `spawn_blocking` work is never cancelled.** `crates/manager-wizard/src/ops.rs:457-462`, `src/lib.rs:1069-1090`. `kill_on_drop` kills only the direct child (Prisma's Node grandchildren survive and hold venv files), and timed-out extraction steps keep writing in the background, racing the retry; a start-gateway timeout after spawn leaves a live gateway recorded as Failed.

Runner-up Majors worth triage in the same pass: drift check blind to spawn-only inputs (wizard M3), raw-flag-only placements destroyed by the CUDA_VISIBLE_DEVICES remap (src-tauri #4), journal entries written after the save with write errors swallowed (src-tauri #3), `--cpu-moe` spelling invisible to detection and the rewrite (models #1), and adapter→GPU misassignment for identical WDDM cards (telemetry).

## Area 1 — manager-models + manager-config

### Major

**1.1 `--cpu-moe` is neither detected nor stripped.** `crates/manager-models/src/memory.rs:193-235` (`expert_offload`), `:114-191` (`set_expert_offload`); cf. `src/lib.rs:246-247`, where the Nemotron catalog comment names `` `--n-cpu-moe`, `--cpu-moe` `` as its fit path (llama.cpp's `-cmoe`/`-ncmoe` short forms are likewise unhandled). A backend with raw flags `--cpu-moe` → detector returns `None` → the requirement counts all ~24 GiB on GPU / 0 system, the slider reads position 0, and placement can report TooLarge for a backend that actually runs at ~2.4 GiB GPU-resident. Worse, `set_expert_offload("--cpu-moe", CpuMoeLayers(8))` yields `"--cpu-moe --n-cpu-moe 8"` and the `None` case leaves `--cpu-moe` in place: the surviving flag wins in llama.cpp, so the operator's chosen offload silently does not take effect — while the detector reads the result back as the target, so the existing round-trip test cannot catch it.

**1.2 Partial MoE offload is priced as a uniform per-layer share but returned with basis `Exact`.** `crates/manager-models/src/memory.rs:296-300`; `src/gguf.rs:297,315,328-334`. The layout keeps only aggregate `expert_bytes` and a block count (per-block sums the parser walks are discarded), so `--n-cpu-moe N` — which offloads the *first* N MoE layers — is priced as `expert_bytes × N / layers`. Both catalog MoE models are Unsloth Dynamic quants whose per-layer expert tensors are deliberately quantized at different rates, so the first-N share is not the uniform share. Nemotron `--n-cpu-moe 16` is asserted in tests as exactly 14,515 MiB system / 9,574 MiB GPU; if the early layers hold more than 16/24 of expert bytes, GPU residency is understated and a split-fit verdict can say "fits" for a load that OOMs. Either compute from per-block sums or downgrade the basis to `Estimate`.

**1.3 GGUF parser: unbounded recursion on nested metadata arrays.** `crates/manager-models/src/gguf.rs:153-161`. The ARRAY case of `read_meta_value` recurses with no depth limit; each level costs 12 bytes of input, so a crafted/corrupt GGUF with ARRAY-of-ARRAY nesting recurses tens of thousands of frames inside the first 8 MiB prefix parse and aborts the process (stack overflow is not a catchable panic) when the layout is resolved for the memory-requirement poll. No test covers nesting.

**1.4 GGUF-derived size math uses unchecked multiplication and silent u32 truncation.** `crates/manager-models/src/gguf.rs:312` (`elements / block * block_bytes`), `:32-37` (`KvGeometry::bytes_per_token`), `:266-270` (`*v as u32` in the metadata getter). No `overflow-checks` profile is set, so release builds wrap. A header claiming one F64 tensor with dims `[2^61]` — never checked against actual file length — computes size 2^64: panic in debug, wraps to 0 in release, so `tensor_bytes`/`expert_bytes` come back near-zero and the "exact" requirement says the model fits anywhere. KV geometry fields at `u32::MAX` overflow the same way; a UINT64 geometry value of `2^32 + 256` for `key_length` is silently truncated to 256, understating KV ~16×.

### Minor

**1.5 `expert_offload` is first-match-wins when both offload spellings are present.** `memory.rs:193-232`. `"--n-cpu-moe 3 -ot exps=CPU"` returns `CpuMoeLayers(3)` (the `-ot` is never examined) while the reversed order returns `AllExperts`; with both flags the process applies both overrides, so the first ordering understates system RAM and the slider reads 3 instead of full. Only hand-written raw flags reach this.

**1.6 `validate()` never validates `display_name`.** `crates/manager-config/src/lib.rs:246-255` (validator exists) vs. the model loop in `validate()` at `:810-830`. A config carrying `"display_name": ""` or a 5,000-char name loads and re-saves cleanly, and since a `Some` name wins over the catalog fallback, the model renders with a blank name. `validate_display_name` also accepts embedded newlines/control characters, which the single-line UI and logs inherit.

**1.7 Placement: `current_split` is validated only by length before it earns credit.** `crates/manager-models/src/placement.rs:153-156` (vs. full validation of the proposed split at `:71-99`). `current_split = [1.5, -0.5]` on the 10 MiB test spec projects `current_mib = [15, 0]` — 15 MiB of credit for a 10 MiB model — so `fits = true` with zero free VRAM and `adjusted_free` is inflated by the same phantom amount. In-tree reachability is limited (the caller passes a config-validated split), but the function itself promises stale splits earn no credit, and an out-of-range split is stale by definition.

**1.8 Test gaps in the new surface.** `crates/manager-config/tests/config_roundtrip.rs:36` round-trips only `display_name: None`, so a save-side field drop would pass; `gguf.rs` tests (`:417-433`) cover only bad magic and a truncated tail — none of findings 1.3/1.4 is guarded; the multi-GiB `sha256_hex` regression test (`manager-models/src/lib.rs:1635-1636`) is `#[ignore]`d, so default CI never executes the v0.1.31 crash-class guard.

### Reviewed and found clean

GGUF reader bounds (`take()` checked arithmetic, `Incomplete`/`Invalid` on truncation, saturating totals, no header-count-driven allocation); expert-tensor identification (stacked `*_exps` and per-expert forms, shared experts excluded, `moe_block_count` counts distinct blocks); KV layer counting (`div_ceil`, errors conservative); `memory_requirement` degradation (unresolvable offload falls back to all-on-GPU at `Estimate`, expert bytes clamped, `div_ceil` MiB on both sides); offload bands/layer round-trips incl. 0 layers; `set_expert_offload` core rewrite (both `--n-cpu-moe` spellings, sibling `-ot` assignments preserved, trailing valueless `-ot` kept); placement credit mechanics (per-GPU, length mismatch earns zero, shrinking share needs zero additional, KV/compute correctly not credited since they sit in *used* VRAM while the backend runs); catalog definitions (serde defaults on new fields, pins internally consistent and test-locked; `CATALOG_REVISION` staying 2 is correct — no persisted state changed); config rename plumbing (`display_name` serde default + skip-if-none, refresh never touches `display_name`/`enabled`/`assigned_backends`, refresh-flag preservation test); `sha256_hex` (bounded 1 MiB buffer, incremental, I/O errors mapped, no unwraps; `verify_sha256` pre-validates the pin and hashes on `spawn_blocking`).

## Area 2 — manager-wizard + manager-gateway

Scope note: the busy-rejection tracker and the diagnostics bundle live in `src-tauri/src/main.rs` (outside this area); this section reviews the wizard-side contracts they rely on.

### Major

**2.1 Timeout budgets are mutually inconsistent; the 900 s sub-budgets are unreachable.** Locations and scenario as Top-5 #4. The trait doc's claim that long jobs "use `run_command_with_timeout`" is false for the real ops implementation: the effective per-command cap is `min(caller, 600 s)`.

**2.2 Timeout does not terminate process trees; `spawn_blocking` work is not cancelled at all.** Locations and scenario as Top-5 #5. Code comments ("a timed-out command is killed rather than left running") overstate both cases.

**2.3 Config-drift check compares only `config.yaml`; spawn-only inputs are invisible, so stale `Done` is adopted.** `crates/manager-wizard/src/lib.rs:650-663`, used at `:797-875`; spawn inputs at `src/steps.rs:3018,3121`. The generated YAML contains no gateway port, no bind host, no DATABASE_URL/postgres state, and only the *name* `os.environ/OPENROUTER_API_KEY`, not the credential. Scenario: gateway running on :4000; the operator changes only `gateway.port` (or `bind_host`, or rotates the credential / changes `cred_ref`, or installs PostgreSQL afterwards). The YAML is byte-identical → drift check passes → the persisted `Done` is adopted → the old gateway keeps serving the old port/key/no-database configuration while the checklist says complete. The gate defeats exactly the stale-gateway problem it was added to solve, for every input that travels via argv/env.

**2.4 Audit verified-by-stamp skip binds the stamp to nothing.** Locations and scenario as Top-5 #3. The log wording is also untruthful on the skip path: no checksum was verified on that run.

### Minor

**2.5 Sustained-health window cannot detect one of the two defects it cites, and can be satisfied by a single slow probe.** `steps.rs:3811-3870`, probe target `:2743`. It probes `/v1/models`, which LiteLLM serves without touching Prisma, so the PrismaWrapper DB-dead defect passes the full 10 s window (only process death is caught; DB-dead is mitigated by the pin, not this check). Separately, each probe can block up to the 15 s HTTP timeout — longer than the window — so one slow 200 returning after the deadline satisfies "10 s of continued answers" with a single observation.

**2.6 Manual block's DATABASE_URL is not paste-runnable: `<port>` placeholder left in the value.** `steps.rs:2607-2611`, against the contract at `src/lib.rs:~254` ("ready-to-run commands"). The real port appears only in the trailing comment; an operator who substitutes only the password pastes an invalid URL. The test at `steps.rs:7494ff` enshrines the placeholder instead of catching it.

**2.7 PowerShell quoting in the manual block is not PowerShell-correct and doesn't neutralize interpolation.** `steps.rs:2552-2576` (`ps_join`/`ps_command_line`), `:2622-2630`. `ps_join` escapes `"` as `\"`, which is not a PowerShell escape; double-quoted args are not escaped for `$`/backtick, so a path containing a `$(...)` segment is evaluated on paste; `tier.cred_ref` is interpolated raw into a double-quoted `$env:` line, so a `"` in it breaks out into code the operator then executes. Inputs are operator-controlled config (limited impact), but the block is presented as safe-to-paste and persisted in reports.

**2.8 Two start-gateway failure paths drop the manual command and the accumulated log.** `steps.rs:4024-4038` vs. the invariant comment at `:3947`. Config-generation failure and the config.yaml write failure return a one-line debug outcome with no manual command and the accumulated log replaced — every other failure path in the step attaches both. A user hitting the new "no enabled model groups" error gets no manual path and loses the preceding log context.

**2.9 `DATABASE_URL` construction trusts any pre-existing stored password verbatim.** `steps.rs:1968-1973`, `src/lib.rs:162-175`. Generated passwords are hex and URL-safe, but `ensure_postgres_password` returns any existing non-empty Credential Manager value unchecked and the URL interpolates it raw; a value containing `@ : / ? #` (older build, manual `cmdkey`, restore) produces a mis-parsed URL — install-postgres succeeds (the raw value is used correctly there) while start-gateway fails opaquely inside LiteLLM with credentials that don't match the cluster.

**2.10 Plaintext `pwfile.tmp` survives if the step future is dropped between write and remove.** `steps.rs:2406-2417`. Removal is straight-line code after the initdb await; the new step-timeout machinery (or an app exit) drops the future in that window and the file containing the postgres superuser password in plaintext remains in `<data_dir>/postgres/` indefinitely. The timeout added in this same diff makes the dropped-future path an in-band occurrence.

**2.11 Elevated-command success can be reported without the process having finished successfully.** `ops.rs:309-330`. Only `WAIT_TIMEOUT` is handled; any other non-success wait result (e.g. `WAIT_FAILED`) falls through to `GetExitCodeProcess`, whose return is ignored, `exit_code` stays at its initialized 0, and the call returns `Ok(0)`. The sole caller treats `Ok(_)` as "rule added/removed" and logs it as fact, so the step can report the firewall reconciled when the outcome was never established.

**2.12 Derived group enablement ignores deployments that don't come from members — WinML / OpenRouter-only groups regressed.** `crates/manager-gateway/src/lib.rs:469-497`, `:543-575`, `:610-633`. Enablement counts only `members`. A group whose backend member is disabled but with `winml.enabled` previously emitted the WinML deployment; now the group is omitted and WinML is unreachable through the gateway. Same for groups whose only deployments would be OpenRouter fallback entries — omitted, and if it's the only group, generation now fails `ConfigInvalid` outright.

**2.13 Global strategy resolution counts disabled members when deciding "multi-member."** `crates/manager-gateway/src/lib.rs:757-766`. Scope was correctly narrowed to enabled groups, but the test is `g.members.len() > 1` over raw members: a group with 1 enabled + 1 disabled member wins strategy priority as if multi-deployment, ahead of a genuinely multi-member enabled group — the global `routing_strategy` can come from a group that generated a single deployment.

**2.14 Tensor-split audit passes an unsplit model against the largest GPU, but unsplit placement is GPU 0.** `steps.rs:1449`. Heterogeneous pair (GPU 0 = 8 GB, GPU 1 = 24 GB), 20 GB unsplit model → audit logs "fits a single GPU" and returns Done (20 ≤ 24), but the backend launches on GPU 0 and OOMs. Audit and runtime disagree about which GPU "a single GPU" is.

**2.15 Timeout test quality: the kill is asserted by comment, not observation.** `ops.rs:1316-1335`; `src/fake.rs:522`. `run_command_with_timeout_bounds_stalled_child` asserts only that the caller returns promptly — never that the `sleep 30` process died — and nothing tests tree-kill or `spawn_blocking` continuation (finding 2.2). The fake's new `Sequence`/`http_get_seq` helpers are sound, but they make scripted success paths easy while the timeout path stays unverifiable in step tests.

### Nit

Reachable only if `hydrate` is called on an instance that already adopted the step.

## Area 3 — manager-telemetry

### Blocker

**3.1 DXGI descriptor struct is 8 bytes too small; `GetDesc1` writes past it.** `crates/manager-telemetry/src/pdh.rs:320-332` (`DxgiAdapterDesc1`). The locally declared struct omits the trailing `Flags: u32` that the real `DXGI_ADAPTER_DESC1` has (that field is the entire reason DESC1 exists vs DESC): the Rust struct is 304 bytes on x86_64, the real one 312. On the target machine (WDDM A4000 with a backend running), `fixup_wddm_processes` engages every poll → `enumerate_adapters()` → `get_desc1` writes the full 312-byte descriptor through a pointer to the 304-byte stack value — a stack buffer overflow / UB on every poll, at best silent corruption of an adjacent local, at worst a crash, in exactly the configuration the feature was built for. Coordinator re-verified: the struct in the tree ends at `adapter_luid` with no `Flags` field.

### Major

**3.2 PDH readings with `CStatus == PDH_CSTATUS_NEW_DATA` are discarded as invalid.** `pdh.rs:514`. Only `PDH_CSTATUS_VALID_DATA` is accepted, but per Microsoft's PDH documentation `VALID_DATA` means "returned successfully, *unchanged* from last read" and `NEW_DATA` means "returned successfully and *different*" — both are success statuses. `dedicated_usage()` opens a brand-new PDH query on every call (`pdh.rs:462-475`), so there is no meaningful "last read" baseline, and a backend whose allocation is actively changing (model loading, KV growth) reports `NEW_DATA` and is skipped — the WDDM row collapses to `None`, flickering or permanently unknown on real hardware, while all fake-source tests pass.

**3.3 Identical-name GPUs are paired to adapters purely by enumeration-order assumption.** `pdh.rs:129-156` (`map_adapters_to_gpus`). For twin cards, name matching carries zero identifying information — the first unused adapter with that name wins. The only inputs are `(index, name)`; no PCI bus id / UUID / device id is passed in, even though the smi inventory has PCI bus ids and the DXGI descriptor carries `device_id`/`vendor_id` that go unused for matching. Two identical WDDM cards (e.g. 2× RTX A4000) whose DXGI enumeration order differs from nvidia-smi minor-number order get crossed: each backend's dedicated usage is reported on the *other* GPU as a confident `Some(...)` — silently wrong data, worse than the `None` the design otherwise prefers.

**3.4 Positional fallback can cross-assign LUIDs after a partial name match.** `pdh.rs:158-163`. The fallback zips unmatched GPUs in index order against remaining adapters in enumeration order — valid only if the orders interleave identically, which a partial name match already disproves. Scenario: GPUs 0 and 2 fail name matching (a suffix variant the normalizer at `pdh.rs:111-121` doesn't strip), GPU 1 matches; DXGI enumerates the leftovers as [adapter-of-2, adapter-of-0] → the zip assigns adapter-of-2 → GPU 0 and adapter-of-0 → GPU 2. An extra enumerated NVIDIA adapter (in DXGI, absent from the smi poll) shifts the zip the same way.

### Minor

**3.5 `phys_<n>` is discarded and readings overwrite instead of summing.** `pdh.rs:92-107` (parser drops the suffix), `pdh.rs:197` (`insert`). A pid with two `GPU Process Memory` instances for one LUID (`..._phys_0`, `..._phys_1` — linked/multi-adapter configurations) produces two readings with the same `(pid, luid)`; the second overwrites the first instead of adding, under-reporting by the other instance's full amount, with the winner able to flap between polls.

**3.6 PDH buffer contents are trusted without length/alignment validation; a growth race kills a whole poll.** `pdh.rs:496-525`. (a) `count` from the second `PdhGetFormattedCounterArrayW` is used in `slice::from_raw_parts` without checking `count × size ≤ buffer.len()`; (b) the instance-name scan walks `szName` to a NUL with no bound against the buffer end; (c) the backing store is `Vec<u8>` (alignment 1) reinterpreted as a pointer-bearing struct array (alignment 8). Safe only while the provider honors its contract. Functionally: if a process spawns between the sizing and fill calls, the fill returns `PDH_MORE_DATA` and `pdh.rs:503-505` turns it into a whole-`readings()` error instead of re-sizing — every WDDM row goes `None` for that tick (self-heals next poll).

**3.7 Standalone `processes()` swallows sample failure and returns un-fixed rows.** `pdh.rs:239-249` (`unwrap_or_default()` at :248). If the follow-up `sample()` fails, the WDDM set is empty and inner rows pass through untouched — safe with today's in-crate sources (smi WDDM rows are already `None`), but it breaks the decorator's own invariant ("on a WDDM GPU the incoming value is never trusted") for any future source yielding a numeric WDDM figure, which is the NVML wiring `lib.rs` describes. The path is also non-atomic (processes, samples, PDH are three separate snapshots), so a pid exiting/reused between them can be attributed using another tick's driver-model set.

**3.8 Sub-0.5 MiB dedicated allocations round down to a measured `Some(0)`.** `pdh.rs:533-538`. `(bytes + 512 KiB) / 1 MiB`: a real non-zero allocation under ~0.5 MiB (e.g. a 200–400 KiB context) is reported as `dedicated_mib: 0` and installed as `Some(0)` — indistinguishable from a genuinely measured zero, the inverse of the bug class this change fixes, able to re-trigger "context only / not resident" conclusions in consumers keying off `Some(0)`. The comment's 256 MiB rationale doesn't match the rounding code.

**3.9 Synchronous blocking FFI runs on the async runtime thread every poll.** `pdh.rs:252-258`. `sample_with_processes` calls the sync fixup (DXGI enumeration + full PDH open/collect/close) with no `spawn_blocking` and no caching. PDH first-load/collect can block for hundreds of ms; at the 1 s cadence this stalls the Tokio worker running the poller every tick, though only the adapter mapping is cacheable work being repeated.

**3.10 Test quality: the entire Windows FFI layer is untested; mapping edge cases untested.** `pdh.rs:545-778`. All tests use `FakeCounters`/`StubInner`; nothing exercises `pdh_query::dedicated_usage` or `dxgi::enumerate_adapters` (both `#[cfg(windows)]`, so they don't even compile-check in a Linux CI run) — precisely where the Blocker and finding 3.2 live. Also missing: identical-twin name mapping, partial-match fallback ordering, multi-`phys` readings for one (pid, LUID), a high-bit LUID (signed→`u32` bit preservation at `pdh.rs:429`), uppercase/`0X` hex in instance names, and a serde regression test that a pre-0.1.32 `ProcessSample` payload still deserializes.

### Reviewed and found clean

LUID construction/normalization (`pdh.rs:82-89, 427-430` — signed HighPart bits preserved, hi/lo order matches the PDH instance format); PDH handle lifecycle (`QueryGuard` closes on every error path; fresh query per call, so a failed poll can't poison the next); DXGI COM mechanics other than the descriptor struct (vtable slots correct — Release 2, `EnumAdapters1` 12, `GetDesc1` 10 — IID correct, exactly-once release on success and traced error paths, `DXGI_ERROR_NOT_FOUND` checked first); error→unknown semantics in the fixup (adapter/readings failure collapses every WDDM row to `None`, never 0; TCC and unknown-model rows pass through; early return when no WDDM GPU exists); bytes↔MiB convention (`largeValue` is bytes for this counter, negatives clamped — rounding nit in 3.8 aside); smi.rs changes (`current_dm` parsed case-insensitively from the correct relative key, unrecognized → `None`; WDDM `N/A` → `None` while TCC numerics and literal `0 MiB` → `Some(...)` — real zeros preserved, no new panic paths); lib.rs serde compatibility (`driver_model` defaulted on both types; `vram_mib: u64 → Option<u64>` is JSON-compatible forward, and there is no persisted or mixed-version `ProcessSample` channel in-crate — the store is in-memory only); store.rs (diff is test-only fixtures); Cargo.toml (windows-sys 0.61 correctly Windows-gated, features cover the usage, DXGI deliberately link-only); nvml.rs (unchanged stub, never fabricates a value the fixup could trust); name normalization basics (case/whitespace/prefix handling for the documented DXGI-vs-smi asymmetry; non-NVIDIA adapters excluded when NVIDIA adapters are present).

## Area 4 — src-tauri

### Major

**4.1 `record_change` and `cancel_target` were never updated to scoped resolution — resolved backend entries never prune, the snapshot never resets, and cancel can revert already-activated changes.** `src-tauri/src/activation.rs:124-139` (`unresolved_entries`), `:199-225` (`record_change`, condition at 207-213), `:250-270` (`cancel_target`); `src-tauri/src/main.rs:3863-3867`. `unresolved_entries` passes an empty start-time map, so every backend-scope entry counts as unresolved forever (only deleted targets escape). Scenario: flags change E1 (snapshot S0) → backend restarts → the scoped plan correctly shows nothing pending, but the journal still holds E1+S0. A second change E2 is recorded; the prune/reset branch never fires, so E2 appends under S0 — cancelling what the plan presents as only E2 restores S0 and silently reverts the already-live E1. Same after `gateway_activation_complete`: the retained backend entry + snapshot let a later cancel restore S0 with `cancelled: true` while the scoped plan said nothing was pending. The journal file also grows monotonically — no path ever removes a resolved backend entry. (Coordinator re-verified the empty-map call in `unresolved_entries`.)

**4.2 Telemetry initialization awaits an unbounded `nvidia-smi` call inside the `OnceCell` init.** `src-tauri/src/main.rs:502-540` (inventory query at 525-532), consumed by `ensure_backend_specs` at `:1288-1300`. `NvidiaSmiSource::run_query` has no timeout. If `nvidia-smi` hangs (driver lockup), the init future never completes and `ensure_backend_specs`, `start/stop/restart_backend`, `list_backends` (via adoption), `placement_propose/apply`, and `model_assign`'s GPU-count check all hang indefinitely. Separately, if that one query merely fails or parses empty at first use, inventory stays empty forever (no retry, no log): every launch silently falls back to unrestricted, losing the VRAM saving the feature exists for, until the app restarts.

**4.3 Backend-scope journal entries are written after the config save, and journal write failures are swallowed.** `activation.rs:94-102` (`save_journal` ignores serialization/write/rename errors), `:199-229` (`record_change` returns `()`); producers `main.rs:2750-2769` and call sites `:3197, :3468, :3563, :4515, :5120-5134` — all after `manager_config::save` succeeded. Kill/crash the app (or fail the journal write) in between and the change is on disk with no journal entry. Gateway-scope changes have a safety net (`config_drift`, `activation.rs:178-186`); backend-scope changes (flags, offload, split, model assignment) do not — they are absent from the generated YAML by design. The plan shows nothing pending, the running backend is never prompted to restart, and the commands still returned `persisted: true`.

**4.4 Placement is inferred only from the structured tensor split, so raw-flag device selection is destroyed by the new remapping.** `main.rs:1006-1030` (`backend_gpu_visibility`), remap block `:1220-1280`. A backend with an empty `tensor_split` is assumed to live on GPU 0; its raw flags — settable through `backend_apply_config` — are then remapped against that assumption. A backend configured raw-only with `--main-gpu 1` (or `--device CUDA1`, or a raw `--tensor-split`) that launched on GPU 1 before this change now gets `CUDA_VISIBLE_DEVICES=<uuid of GPU 0>`, its `--main-gpu`/`--device` dropped as "unplaced" and its raw split discarded — it silently moves to GPU 0, where it can OOM or displace the backend placed there. The function docs call placement "the source of truth", but nothing migrates or warns about raw-only placements.

### Minor

**4.5 Journal load-modify-save is unsynchronized.** `activation.rs:94-102, 199-229`; `main.rs:5118-5134` (placement records under a config *read* lock), `:3863-3867` (complete takes no lock). Most commands accidentally serialize by recording under the config write lock; `placement_apply` and `gateway_activation_complete` don't, so a concurrent `record_change` vs `clear_gateway_scope` (or two placement applies) interleave load→append→save — last save wins, losing a backend entry (untracked change, as in 4.3) or resurrecting cleared gateway entries.

**4.6 `placement_apply` captures state under a read lock and only re-checks existence under the write lock.** `main.rs:5022-5070` (capture), `:5075-5134`. A concurrent `model_assign` in the gap means the split is applied to a backend that no longer serves the model, and the journal snapshot is the stale pre-assign config; `cancel_target`'s guard compares only against the last entry's `config_after`, so it passes and the cancel discards the intervening assignment.

**4.7 `raw_flags_pin_cpu_only` returns true on the *first* 0-valued `-ngl`, ignoring a later override.** `main.rs:1032-1052`. llama.cpp parses flags sequentially (last wins): `-ngl 0 -ngl 99` ends at 99 GPU layers, but this classifies the backend CPU-only — `CUDA_VISIBLE_DEVICES=""`, structured split and `--main-gpu`/`--device` dropped. Behavior depends on flag order in a way the launch itself does not.

**4.8 `backend_set_offload` validates `layers` against a `moe_layers` read under a read lock and never rechecks under the write lock.** `main.rs:3512-3532`, `:3534-3572`. A `model_assign` in between can swap the backend to a model with fewer MoE layers (48 → 24); the command then persists `offload_for_layers(layers, 48)` — up to `--n-cpu-moe 40` or the all-experts form — for the 24-layer model. `manager_config::validate` knows nothing of MoE counts, so the bad config saves cleanly and the backend fails/misloads at next start.

**4.9 `get_logs`: `truncated` contradicts its documented meaning once `offset > 0`.** `main.rs:2560-2572` (docs), `:2655-2660`. With total 250, offset 200, limit 200 → a 50-record page reports `truncated: false` despite 200 records skipped before the page. A UI using `truncated` to signal omitted context shows none for exactly the deep-page case.

**4.10 `get_logs` `since_ms`/`until_ms` cannot actually filter file-backed scopes.** `main.rs:2424-2456`, `:2520-2548`, filter at `:2640-2646`. Every gateway/wizard line is stamped with its file's mtime; `wizard.log` accumulates a full day and gateway logs a whole run, so a `since_ms` of one hour ago returns every line in the file, including day-old ones — for wizard records the real per-line RFC 3339 timestamp sits in the line text, ignored. The doc comment ("the comparison is direct") overstates what the filter delivers for these scopes.

**4.11 `list_backends` does synchronous GGUF reads under the supervisor lock; the layout cache key uses 1-second mtime granularity.** `main.rs:1480` (lock held for the whole command), `:1518-1565`, `:4609-4655`. For an uncached model whose header doesn't parse in 8 MiB, the probe reads 8+64+256 MiB synchronously while the supervisor mutex is held, stalling start/stop/status for all backends on that poll. Afterwards, a file replaced within the same second at the same length keeps the stale cached layout — wrong expert bytes / MoE count for the slider and memory figures — because the key is `(path, len, mtime_secs)`.

**4.12 Memory-requirement total silently mixes sources while labelled `Exact`.** `main.rs:4688-4710` (`resolve_weight_layout`). With a catalog entry, `total_bytes` is the catalog pin regardless of the file on disk; when the GGUF parses, `basis` upgrades to `Exact` and expert bytes come from the file, but the total stays the catalog's. Replace the GGUF at the same path with a different quant and `list_backends` reports figures computed from two different files, labelled exact.

**4.13 Catalog-definition refresh rides the new offload value with no activation journal entry.** `main.rs:~805-830`, save at `~855-870`. On the first `list_models` after a catalog-revision bump, the refresh clears the coder's split, rewrites its raw flags, and can clear the planner's split — saved best-effort (`let _ = save`) with no gateway- or backend-scope journal entry. Running backends diverge from disk with no restart prompt; the next natural restart picks the new serving config up unannounced. (The refresh mechanism predates this diff; v0.1.32 changes the offload value it applies and adds the backend-scope journal it could have used.)

**4.14 `model_set_short_name` offers no way to clear an override.** `main.rs:4291-4307`. `validate_display_name` rejects empty input, so once set there is no API path back to the catalog name; if the catalog later renames the model, the stale override shadows it forever short of hand-editing the config.

**4.15 Test gaps for the new behavior.** No tests exist for: `clear_gateway_scope` (incl. snapshot retention), any new `get_logs` argument (`query`, `since_ms`/`until_ms`, `order="asc"` mirror, `offset`/`truncated`), `record_change` pruning or `cancel_target` with backend-scope entries, start-time exactly equal to entry ts, `--device=`/`--main-gpu` inline forms in the device remapper (only `--main-gpu=` covered), duplicate `--device` entries, or the `-ngl` override-order case (4.7). The tests that do exist for split remapping and scoped resolution are otherwise good.

### Nits

**4.16 `backend_set_offload` reports `"persisted": changed`.** `main.rs:~3578-3585`. Setting the slider to the value already on disk returns `persisted: false`, which a caller can reasonably read as "not saved" when the desired state is in fact persisted. (`backend_update_flags` returns `persisted: true` unconditionally for the same situation.)

**4.17 `get_logs` `order` is not validated.** `main.rs:2647-2651`. Anything other than exactly `"asc"` — `"ASC"`, a typo — silently yields descending order instead of an error, unlike `backend_apply_config`'s strict `apply_mode` check.

`--device` remapping is injective); deliberately-unrestricted fallbacks (missing/empty UUID, all-zero split → args verbatim, no env, no guessing); CPU-only handling (empty `CUDA_VISIBLE_DEVICES`, split dropped, `-ot exps=CPU` correctly not misclassified for single-occurrence spellings); ## Area 5 — UI

### Major

**5.1 Logs: a page/filter change made while a load is in flight is silently dropped, and the in-flight load then paints mismatched rows/page info.** `ui/src/views/static.ts:2489-2490` (load guard), `:2560-2569` (handlers), `:2523` (pageInfo). `load()` returns immediately when `loading` is true, with no queued/coalesced retry (Backends uses a `loadSeq`; Logs doesn't). Scenario: a `get_logs` fetch is in flight; the operator clicks Next → `page` becomes 2, `load()` no-ops; the in-flight page-1 fetch completes and paints page-1 rows while `pageInfo`/Prev/Next are computed from the mutated global `page` — the UI reads "Page 2 of N" over page-1 lines and no fetch for page 2 ever runs. A filter change mid-flight is the same with the reset to page 1: old-filter results painted under new filter controls. Only a manual Refresh (or the next Follow tick) recovers.

**5.2 Placement-apply and flags-save report "saved" without checking `persisted`.** `ui/src/views/static.ts:1773-1785`, `:1795-1806`, `:1838` (enable/disable, same pattern). Both handlers branch only on `r.error`; `PlacementApplyResult.persisted` is documented (`ui/src/api.ts:1736-1745`) as true only when the split was saved to the configuration file, and flags-save returns the same flag. Scenario: the command succeeds in memory but the config write fails (`persisted: false`, no error) → the UI posts "Split saved to \<id\>. Restart the backend to use it." and closes the form; the change is gone on app restart. The same file handles this correctly elsewhere (gateway OpenRouter toggle `:3010`, MXC mode `:3374` both warn on `!persisted`) — these call sites are inconsistent with the codebase's own contract.

**5.3 Dashboard Topology regressed by the new all-backends placement rows.** `ui/src/api.ts:269-275` (fallback segment), `ui/src/views/dashboard.ts:318-345`. In v0.1.30 `placementFromConfig` emitted rows only for backends with a positive tensor split; now every configured backend gets a row with a fabricated 100%-on-GPU-0 segment when unsplit/all-zero. The Appliance view handles this (graying, legend exclusion), but `topologyView` still consumes `m.placement` as models and draws a backend→GPU edge for **every** row regardless of `backendEnabled` or status, plus a model node labelled "100%" — contradicting the comment at `dashboard.ts:306-309` ("never a positional full mesh asserting links the configuration does not have") and the Service Map's rule that a stopped backend resides nowhere. With >4 backends, unsplit rows also crowd genuinely split models out of the 4-node slice.

**5.4 Activation Plan view converts a failed poll into "every saved change is live."** `ui/src/views/static.ts:783-788`, `:766-772`; `ui/src/api.ts:1387-1396`. `wireActivationPlan.load()` assigns `lastPlan = r.data` unconditionally; on invoke failure `getActivationPlan` returns `EMPTY_PLAN` (`pending: false`) **with** `r.error` set, which the view never checks — so it paints "No activation plan pending / Every saved configuration change is live." If `gateway_activation_plan` fails on first load or on one 10 s poll while changes are genuinely pending, the dedicated view asserts the opposite of the truth. The global banner gets this right (`ui/src/main.ts:97-102` keeps last known state on error), as do the Backends/Gateway plan loads (`!pr.error` guards).

### Minor

**5.5 Logs "To" bound drops the final minute's seconds.** `ui/src/views/static.ts:2398-2400`, `:2455-2460` (`msOf`), `:2496-2503`. `msOf("…T14:30")` is 14:30:00.000 and is sent as the *inclusive* `untilMs`; lines timestamped 14:30:01–14:30:59 are excluded server-side, so bracketing an incident "to 14:30" silently loses everything in that minute after :00. **5.6 Logs clamp refetches only once and can still land on a non-existent page.** `ui/src/views/static.ts:2511-2516`, `:2522-2523`, `:2531-2536`. If the filtered total shrinks again between the clamp fetch and the refetch (lines aging out of the 10k ring under Follow), `page` remains > the recomputed `pages`: pageInfo prints "Page 5 of 3 · N matching records" and the body says "No lines match the current filters" although N > 0. The clamp needs a loop or a post-refetch re-clamp.

**5.7 Placement projection is not invalidated when the backend's model changes.** `ui/src/views/static.ts:1533`, `:1758`, `:1767-1777`, `:1888-1917`. Chip changes clear `placeProjection`; nothing else does. Open Placement, Propose for model A, then change the card's model dropdown to B (the form stays open; the projection is re-attached by `backendId` alone at `:1314`): the fit table still prices model A's weights, and Apply calls `placementApply(proj.modelId /* A */, …)` — applying A's split while the card presents B as the backend's model.

**5.8 Poll repaint destroys focus for in-card controls other than the offload slider.** `ui/src/views/static.ts:1403-1405`, `:1300-1321`. The 5 s Backends poll skips painting only when the offload slider is focused; the flags Custom ctx/batch inputs (`:1072`, `:1080`) and the placement GPU checkboxes are recreated by every other poll — a user mid-typing in Custom context loses focus/caret (the synced draft keeps the partial value, e.g. "65" for an intended 65536, which can then be Saved), and a keyboard user toggling several chips loses focus after the first repaint. **5.9 Per-backend card state is never pruned when a backend disappears, and leaks onto a re-created backend with the same id.** `ui/src/views/static.ts:1200-1226`, `:1388-1402`, `:1809-1832`, card at `:940-944`. `load()` prunes `msgs`/`confirmRemove` only on a state change of a surviving row; nothing prunes `msgs`, `openMenus`, `openArgv`, `argvCache`, `confirmRemove` for vanished ids. In one Backends mount: open backend `coder`'s Launch command, remove `coder`, re-add a backend named `coder` (different model/port) → the new card renders with its argv panel already open showing the **previous** backend's cached launch command, plus any stale card note.

**5.10 Service Map residency map overwrites instead of summing per (backend, GPU), and the new null value makes it order-dependent.** `ui/src/views/serviceMap.ts:396-403`. One entry per backend/GPU is kept — the last process wins. A backend with two attributed processes on one GPU shows only the last one's MiB (understating held VRAM, possibly dropping a ≥1 GiB residency below the edge threshold); with nullable `vram_mib`, if the last process is unmeasured it overwrites a measured value and the backend renders "residency not measured", and reversed order silently hides the unmeasured one. **5.11 smoke.mjs asserts presence only; none of the new behavior is covered.** `ui/scripts/smoke.mjs:35`. The activation-plan commands aren't even in the presence list, so dropping the banner/activation route would also pass.
